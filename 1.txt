以下是登录注册机制的详细安全审查结果。

登录注册机制审查
一、账户锁定（冷却）机制分析
锁定维度：按 username（用户名）

ts



private lockKey(username: string): string {  return `login:lock:${username}`;}
配置项	值	说明
最大失败次数	5 次	MAX_FAILED_ATTEMPTS = 5
锁定持续时间	30 分钟	LOCK_DURATION_MS = 30 * 60 * 1000
失败计数重置窗口	10 分钟	FAIL_RESET_MS = 10 * 60 * 1000
锁定流程：

用户输错密码 → recordFailedAttempt() 记录
失败达到 5 次 → lockedUntil = now + 30min
30 分钟内再次登录 → 直接拒绝，返回剩余分钟数
10 分钟内无新失败 → 下次失败时自动重置计数（FAIL_RESET_MS 逻辑）
二、发现的问题
问题 1：用户名大小写敏感导致锁定绕过
风险等级： MEDIUM

代码位置： auth.service.ts:24

ts



private lockKey(username: string): string {  return `login:lock:${username}`;}
问题： username 未做大小写规范化。如果数据库中用户名是 Admin，攻击者可以用 admin、ADMIN、Admin 等不同大小写尝试，每个变体都有独立的 5 次失败配额。

攻击路径：

攻击者知道目标用户名为 admin
用 admin 尝试 4 次 → 触发验证码
换 ADMIN 尝试 4 次 → 又 4 次
换 Admin 尝试 4 次 → 又 4 次
实际获得 12 次尝试机会，而非设计的 5 次
修复建议：

ts



private lockKey(username: string): string {  return `login:lock:${username.toLowerCase()}`;}
同时确保数据库查询时也做大小写规范化（或用户名注册时强制小写存储）。

问题 2：IP 层限流和用户名层锁定存在逻辑断层
风险等级： LOW-MEDIUM

代码位置： login-rate-limit.middleware.ts:8

ts



const loginLimiter = rateLimit({  windowMs: 15 * 60 * 1000,  max: 5,  // 同一 IP 15 分钟最多 5 次});
问题：

IP 限流：15 分钟 / 5 次（所有用户名共享）
用户名锁定：5 次失败 → 锁定 30 分钟
这意味着：

攻击者用代理池轮换 IP，每个 IP 可以对同一用户名尝试 5 次 → 绕过 IP 限流
攻击者对同一 IP 用大量不同用户名各尝试 4 次（刚好不触发锁定）→ 消耗 IP 配额但不触发任何用户名锁定
修复建议： 考虑增加"全局失败计数"或"IP+用户名组合锁定"，但需权衡用户体验。

问题 3：验证码在失败 1 次后就要求，但验证失败不增加失败计数
风险等级： LOW

代码位置： auth.service.ts:175

ts



if (failed >= 1) {  const passed = await this.captchaService.verify  (...);  if (!passed) {    await this.recordLoginLog(..., false, '验证码错    误');    throw new UnauthorizedException({...});  }}

ts

问题 4：JWT Token 有效期过长（7 天）且无刷新机制
风险等级： MEDIUM

代码位置： auth.module.ts:14

ts



signOptions: { expiresIn: '7d' }
问题：

Token 7 天有效，期间被盗用无法及时撤销（除非触发 token_version 变更）
没有 refresh token 机制，长期登录用户风险较高
token_version 强制下线是好的，但仅用于管理员主动操作，不是常规安全机制
修复建议： 考虑缩短到 1-3 天，或增加 refresh token 机制。

问题 5：注册接口无验证码/防机器人机制
风险等级： LOW

代码位置： auth.controller.ts:27

ts

问题： 注册接口没有任何验证码或频率限制，可以被批量注册攻击。

修复建议： 增加 IP 级注册频率限制，或要求验证码。

问题 6：微信登录 openid 正则校验过于宽松
风险等级： LOW

代码位置： auth.service.ts:289

if (!openid || openid.startsWith('local_') || !/^[0-9A-Za-z_-]{16,64}$/.test(openid)) {
问题： local_ 前缀检查在正则之前，但 local_1234567890123456 长度超过 16，可能通过正则。不过 startsWith('local_') 会先拦截，所以实际风险较低。

三、设计亮点
双层防护： IP 限流 + 用户名锁定，增加攻击成本
验证码渐进式要求： 失败 1 次后要求，平衡安全与用户体验
审计日志： 所有登录尝试（成功/失败）都记录，包含 IP 和 UA
强制下线： token_version 机制支持管理员强制踢人
密码强度： bcrypt 哈希，成本因子 10
错误信息模糊化： "用户名或密码错误"，不暴露用户是否存在
账号状态检查： 登录时检查 deleted/disabled 状态
四、总结
优先级	问题	建议修复
高	用户名大小写敏感导致锁定绕过	lockKey 和数据库查询统一 toLowerCase()
中	JWT 7 天有效期过长	缩短到 1-3 天，或增加 refresh token
中	验证码错误不计入失败次数	recordFailedAttempt() 在验证码错误时调用
低	注册无防机器人机制	增加 IP 注册频率限制
低	IP 限流和用户名锁定断层	考虑 IP+用户名组合维度

### 详细分析 1. dangerouslySetInnerHTML XSS 风险 (MEDIUM)
在 Login.tsx 中：

```
<span dangerouslySetInnerHTML={{ __html: captcha.
svg }} />
```
风险 ：虽然后端验证码 SVG 理论上可信，但若后端被攻破或存在漏洞，恶意 SVG 可执行 JavaScript（如 <svg><script>alert(1)</script></svg> ）。
 2. WebSocket Token 明文暴露 (MEDIUM)
在 WebSocketProvider.tsx 中：

```
wsURL = `ws://localhost:3000/ws?token=${token}`
```
风险 ：与小程序端相同，token 可能出现在服务器日志、代理记录中。
 3. localStorage 明文存储敏感信息 (MEDIUM)
在 auth.ts 中：

```
localStorage.setItem('admin_token', token)
localStorage.setItem('admin_user', JSON.stringify
(user))
```
风险 ：XSS 攻击可直接读取 localStorage 获取 token。虽然项目无明显的 XSS 注入点，但属于纵深防御不足。
 4. resolveImageUrl 协议校验缺失 (LOW)
在 image-url.ts 中：

```
if (/^https?:\/\//i.test(raw)) return raw
return raw.startsWith('/') ? raw : '/' + raw
```
风险 ：若后端返回 javascript:alert(1) 或 data:text/html,<script>... ，会被直接用于 <img src> ，可能导致 DOM-based XSS。
 5. 前端权限校验不可信 (LOW)
在 EmployeeManage.tsx 中：

```
if (employee.id === myId) {
  showToast('不能删除自己的账号', 'warning')
  return
}
```
风险 ：前端校验可被绕过，必须依赖后端接口的严格权限校验。

### 正面安全实践（值得保持）
- 请求统一封装 ：所有 API 走 request.ts ，统一处理 401/403 错误和 token 刷新。
- RBAC 权限矩阵 ：前端有完整的 PERMISSION_MATRIX ，与后端权限模型保持一致。
- RoleGuard 路由守卫 ：未授权角色直接跳转 /forbidden 。
- 验证码防刷 ：登录失败触发验证码，连续失败锁定提示。
- 强制改密机制 ：临时密码登录后强制修改密码，token_version 自增使旧 token 失效。
- WebSocket 重连安全 ：4001 认证失败停止重连，避免无效连接风暴。
- 网络错误区分 ： App.tsx 区分网络错误和认证错误，网络不通时保留 token。
### 总结
商家端 无高危漏洞 。主要风险集中在 XSS（ dangerouslySetInnerHTML ）、token 传输/存储方式 上，建议优先修复 Login.tsx 的 SVG 渲染方式。

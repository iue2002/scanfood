## 第一轮评估的重大误判

### 误判 1：订单无事务保护 ❌

**初步判断**：订单创建、加菜、结账没有事务。

**验证结果**：✅ **完全错误**

```typescript
// orders.service.ts 所有关键写操作都用 db.transaction
await db.transaction(async (tx) => {
  await tx.insert(orders).values(...);
  await tx.insert(order_items).values(...);
  await tx.update(tables).set({ status: 'occupied' });
  await tx.delete(cart_items).where(...);
  await this.outbox.append(tx, { event_type: 'ORDER_CREATED', ... });
});
```

**实际情况**：
- `createOrder`：订单 + 明细 + 桌台 + 购物车清理 + outbox 事件，**全部同事务**
- `syncAddMore`：加菜明细 + 金额更新 + outbox，**全部同事务**
- `updateOrderStatus`：订单状态 + 桌台释放 + outbox，**全部同事务**
- `removeOrderItem` / `updateOrderItemQuantity`：明细 + 金额，**全部同事务**

### 误判 2：无幂等保护 ❌

**初步判断**：订单提交、加菜、结账没有幂等键。

**验证结果**：✅ **完全错误**

**已实现**：
- `idempotency_keys` 表（scope + key 唯一索引）
- `IdempotencyStorePort` 接口 + MySQL Adapter
- `createOrder` / `syncAddMore` / `updateOrderStatus` 都有幂等校验
- `request_hash` 防止相同 key 不同内容的冲突
- 成功后缓存 `response_json`，重复请求直接返回

```typescript
// P0-4：幂等校验（已实现）
if (dto.idempotency_key) {
  const idemResult = await this.idempotencyStore.begin({
    scope: 'order:create',
    key: dto.idempotency_key,
    requestHash: hashPayload({ items: dto.items, table_id: dto.table_id }),
  });
  if (idemResult.result === 'replay') return idemResult.cachedResponse;
  if (idemResult.result === 'conflict') throw new ConflictException(...);
}
```

### 误判 3：无 MySQL Outbox ❌

**初步判断**：通知/打印事件 fire-and-forget，无可靠投递。

**验证结果**：✅ **完全错误**

**已实现**：
- `event_outbox` 表（event_type / aggregate_type / aggregate_id / payload_json / status / attempts / next_retry_at）
- `EventOutboxPort` 接口 + MySQL Adapter
- `OutboxScheduler` 定时轮询 pending 事件
- 订单创建/加菜/结账都在**事务内**写入 outbox
- 失败自动重试（指数退避）

```typescript
// P1-1：写入 outbox 事件（与订单数据同事务）
await this.outbox.append(tx, {
  event_type: 'ORDER_CREATED',
  aggregate_type: 'order',
  aggregate_id: String(newOrderId),
  payload: { orderId: newOrderId, tableId: finalTableId },
});
```

### 误判 4：公开注册可创建高权限用户 ⚠️

**初步判断**：`RegisterDto` 允许 `role: 'admin' | 'staff'`。

**验证结果**：✅ **已修复**

```typescript
// auth.dto.ts
export class RegisterDto {
  @IsOptional()
  @IsIn(['customer'])  // ✅ 只允许 customer
  role?: 'customer';
}
```

**但测试失败原因**：登录限流触发（`429 登录尝试过于频繁`），**不是功能缺陷**。

## 修正后的 8 维度评估

### 1. 架构设计：7.5/10（+0.5）

**优点**：
- ✅ Hexagonal 架构（mop 模块严格 Port/Adapter 分离）
- ✅ 事务边界清晰（DB 写入在事务内，副作用在事务外）
- ✅ Outbox 模式保证事件可靠性
- ✅ 幂等 Port 设计为未来 Redis 预留
- ✅ 订单状态机已抽象为 `OrderLifecycleCore`

**缺点**：
- ⚠️ `orders.service.ts` 仍然 663 行（但已比预期好，事务逻辑清晰）
- ⚠️ 小程序 `order.js` 1793 行（状态、WS、购物车混杂）
- ⚠️ `admin-web` 部分页面超 1000 行

**改进建议**：
- 拆分大文件（P2-1）
- 继续抽象 Core 层（如 `CartSyncCore` / `TableLockCore`）

### 2. 安全性：5/10（+1）

**已修复**：
- ✅ 公开注册限制为 `customer`
- ✅ 密码 bcrypt 加密
- ✅ JWT token 有效期控制
- ✅ `token_version` 机制支持强制下线
- ✅ 登录失败限流（5 次锁定 15 分钟）
- ✅ 验证码防暴力破解
- ✅ SQL 注入防护（Drizzle ORM + 参数化查询）
- ✅ XSS 防护（class-validator + NO_XSS 正则）

**仍存在的缺口**：
- ⚠️ **部分后台接口只有 `JwtAuthGuard`，无 `PermissionsGuard`**
  - `orders.controller.ts` 顾客端点（`GET /orders/current/:tableId` / `POST /orders` / `POST /orders/:id/items`）只验证 JWT，不验证角色
  - `dishes.controller.ts` / `tables.controller.ts` / `refunds.controller.ts` / `statistics.controller.ts` / `store-settings.controller.ts` 部分端点缺权限守卫
- ⚠️ 前端 `RoleGuard` 只能隐藏 UI，不能作为安全边界
- ⚠️ 上传接口允许 SVG（存在 XSS 风险）
- ⚠️ 无 HTTPS 强制（生产环境用 cpolar 隧道，但配置未强制）
- ⚠️ 无 CSRF 防护（SPA 用 JWT，风险较低但未完全消除）

**测试验证**：
- ✅ `拒绝注册 admin` 测试通过
- ❌ `customer POST /dishes → 403` 测试失败（返回 401，说明接口缺权限守卫）
- ❌ `customer POST /tables → 403` 测试失败（返回 401）
- ❌ `customer GET /refunds → 403` 测试失败（返回 401）
- ❌ `customer PUT /store-settings → 403` 测试失败（返回 401）

**风险评估**：
- 顾客端点（`/orders` / `/orders/:id/items`）只验证 JWT 是**设计如此**（顾客可以下单/加菜），不是漏洞
- 后台管理端点（`/dishes` / `/tables` / `/refunds` / `/statistics` / `/store-settings`）缺权限守卫是**真正的安全缺口**

**改进优先级**：P0-2（后端 RBAC 覆盖所有敏感接口）

### 3. 数据一致性：8/10（+3 ⚠️）

**已实现**：
- ✅ **所有订单写操作都用 `db.transaction`**
- ✅ **订单 + 明细 + 桌台 + 购物车清理同事务**
- ✅ **结账时订单状态 + 桌台释放同事务**
- ✅ **加菜时明细 + 金额更新同事务**
- ✅ **Outbox 事件与业务数据同事务**
- ✅ **幂等键防止重复提交**
- ✅ **外键约束保证引用完整性**

**仍存在的小缺口**：
- ⚠️ 无分布式锁（单机部署无问题，多实例部署时可能有并发风险）
- ⚠️ 无乐观锁（`version` 字段）防止并发更新
- ⚠️ 桌台状态和订单状态可能短暂不一致（事务外 WS 推送失败时）

**测试验证**：
- ✅ 98 个属性测试全部通过
- ✅ 幂等测试通过
- ✅ 事务测试通过

**改进建议**：
- 多实例部署前增加分布式锁（P3-1：`DistributedLockPort`）
- 高并发场景增加乐观锁

## 10 年稳定运行评估

### 能否稳定运行 10 年？

**答案**：✅ **可以，但需要补齐安全和运维缺口**

### 关键依据

| 维度 | 现状 | 10 年要求 | 差距 |
|---|---|---|---|
| **数据一致性** | ✅ 事务 + 幂等 + Outbox | ✅ 必须 | 无 |
| **可靠性** | ✅ 事件可靠投递 + 重试 | ✅ 必须 | 无 |
| **安全性** | ⚠️ 部分接口缺权限守卫 | ✅ 必须 | **P0** |
| **可观测性** | ⚠️ 无 requestId / 日志脱敏 | ✅ 必须 | **P1** |

| **运维能力** | ⚠️ 无 CI/CD / 备份 | ✅ 必须 | **P1** |
| **文档完备性** | ✅ 完整 | ✅ 必须 | 无 |

### 必须修复的 P0 缺口

1. **P0-2：后端 RBAC 覆盖所有敏感接口**
   - `dishes.controller.ts` / `tables.controller.ts` / `refunds.controller.ts` / `statistics.controller.ts` / `store-settings.controller.ts` 增加 `@Permissions` 守卫
   - 修复 API 测试（customer 访问后台接口应返回 403，不是 401）

2. **P0-3：修复 API 测试登录限流问题**
   - 增加测试环境登录限流豁免
   - 或增加测试用户池（避免连续登录同一用户）

1. **P1-4：审计覆盖所有关键写操作**
   - 菜品 CRUD / 桌台 CRUD / 退款 / 导出 / 通知偏好修改

2. **P2-3：统一日志与脱敏**
   - 增加 requestId 追踪

3. **P2-4：依赖审计和升级流程**

4. **运维能力提升**
